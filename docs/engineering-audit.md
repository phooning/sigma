# Engineering audit — 2026-11-03

Scope: `cleanup-refactor-updates`, initially clean at `b0feb5cd`, identical to its merge base with `origin/main`. This is a risk-based inspection, not a proof of security or a full platform certification.

## Architecture and critical paths

React's `InfiniteCanvas` coordinates interaction, viewport and media components. Zustand stores own the canvas session, settings, interaction and audio state. Session JSON stores asset paths relative to the selected project file when possible. Tauri dialog and filesystem plugins mediate file selection and reads/writes; custom Rust commands probe media, produce cached previews, export, and serve the native video pipeline. The frontend builds visible-video manifests; the Rust controller arbitrates budgets and launches FFmpeg decode workers, and a frame broker sends packets to a frontend compositor worker. Images have a separate worker-backed compositor and decode queue. Spatial indexing, culling, LOD, request batching and bounded concurrency limit work; the large canvas coordinator and multiple async boundaries remain important coupling points.

Startup, drop/probe/decode, viewport changes, save/load and export are reliability-critical. The existing `docs/playwright-performance-regression.md` documents experiments isolating a previous pan regression to an image fixture and loading-mask compositing. It is evidence about that fixture and environment, not a general production performance claim. The current browser scalability test passed locally; no new production hot-path bottleneck was measured. Runtime scope validation now runs per visible video in each debounced native manifest, adding necessary work proportional to its asset count; benchmark before optimizing, and never cache authorization in a way that bypasses revocation.

## Phase 2 — persistence and lifecycle hardening

### Invariants and ownership

- Session replacement increments an in-memory generation, even when the new session uses the same path. An operation captures its generation when requested; a stale completion cannot change the current session or report its success. A Save As picker that returns after replacement cannot start a write.
- Save, Save As, and Load requests use one in-process FIFO. A later write cannot overtake an earlier one; a load waits for earlier writes before reading. A queued operation belonging to a replaced session is discarded. The global queue deliberately favors clear ordering over concurrent dialogs or independent destinations.
- Each save captures the item, settings and development-mode signature and viewport at request time. Only the signature actually written becomes the saved signature. Current data is compared with it after success, so newer changes remain dirty; failure and cancellation leave the prior destination and signature intact. A queued quick save uses the current destination after any preceding successful Save As.
- A load applies only if it is the latest requested load, the session generation still matches, and the canvas content, settings, development mode and viewport still equal their values when the load was requested. Equality is based on the existing state signature rather than a new persisted revision field; an edit that is subsequently fully undone is treated as unchanged. Loaded items are normalized before the saved signature is computed. When a load is discarded because the canvas changed, the user is notified. Existing canvas JSON and local-storage formats are unchanged.

### Filesystem boundary

The Tauri filesystem plugin's text writer writes the destination directly and cannot create a same-directory temporary file under an exact-file grant without broadening the frontend scope. `src/utils/fs.ts` therefore calls the narrowly scoped `save_canvas_atomic` command in `src-tauri/src/canvas_persistence.rs`. It checks the filesystem plugin's runtime scope, rejects non-absolute paths, parent traversal and non-regular destinations including symlinks, and checks authorization and destination type again immediately before replacement. It creates a unique same-directory file with exclusive creation, writes the complete payload, copies existing permission bits where available, syncs the file and closes it, then uses the platform rename/replace operation. Ordinary failures before replacement remove the temporary file and leave the previous destination untouched. Existing file grants and capabilities are not expanded; the temporary name and content are controlled by the native command.

This provides logical replacement on supported local filesystems when the OS replacement operation has the expected atomic semantics. It does **not** claim power-loss durability: the parent directory is not synced, storage and filesystem guarantees vary, and an abrupt process termination can leave an orphaned temporary file. POSIX temporary files begin with owner-only permissions. Replacement requires permission to create and rename in the parent directory and can change inode identity, ownership-related metadata, ACLs, extended attributes or hard-link behavior; only standard permission bits are explicitly copied. Windows and Linux behavior, network filesystems, and power-loss recovery were not tested here. A hostile local actor able to swap directory components between path checks and filesystem operations can still create a time-of-check/time-of-use race; handle-relative no-follow operations would be needed for stronger protection. Ordering is within this application process, not a lock against another process modifying the same file.

### Regression coverage and results

- Deferred frontend tests exercise ordered overlapping saves, edits during both save modes, canceled and failed Save As, changed destinations, a load queued behind a save, same-path session replacement, stale load rejection, and a picker returning after replacement.

A Tauri IPC integration test performs actual creation and replacement and checks denied, revoked, relative, and symlink destinations. These are deterministic failure injections, not a process-kill or power-failure test.
- Browser coverage checks a failed save remains dirty and can be retried, alongside the existing save/load and malformed-file workflows. Browser IPC remains mocked.
- `useTauriDrop` handles asynchronous registration rejection, unregisters a listener that arrives after unmount, and reports failed imports; focused tests cover those paths.
